# 설계 v2 — 원인 검증

> 작성 2026-09-14 · **본 측정 전에 고정한다.** 측정이 끝난 뒤 이 문서의 가설 · 판정 기준 · 제외 규칙을 바꾸지 않는다.
> 바꿔야 하면 바꾼 이유와 시각을 맨 아래 "변경 기록" 에 남긴다.

## 왜 v2 인가

v1 은 조건 26개를 3회씩 쟀지만, 외부 리뷰와 코드 · 원자료 감사에서 결론을 받칠 근거가 부족하다는 것이 드러났다 (README 정정 절).

- 원인 결론("드라이버 pinning 때문에 캐리어가 병목")에 **원인을 없애 보는 실험**이 없었다
- pinning 증거(스택)가 저장되지 않았고, pinned 수는 발생 횟수가 아니었다
- TPS 가 측정창 뒤 요청까지 세어 부풀려졌다
- H3 는 전역 락이라 pinning 과 상호배제를 구분하지 못했다
- CPU · GC · DB 를 재지 않고 "CPU 병목이 아니다" 를 추론했다
- 반복 3회 · 순서 고정 · 편차 기준 없음

## 질문

1. **이 환경(1 core · 1GB)에서 DB 를 건드리는 경로가 VIRTUAL 에서 느린 원인이 드라이버의 monitor pinning 인가?**
2. 그 원인을 없애면(드라이버 교체 · JDK 교체) 어떤 조건에서 VIRTUAL 이 PLATFORM 과 비슷하거나 나아지는가?
3. 코드의 `synchronized` 는 락 범위에 따라 VIRTUAL 에 어떤 영향을 주는가?

## 사전 사실 (공식 문서로 확인)

- **MySQL Connector/J 9.0.0** (2024-07-01): "Synchronized blocks in the Connector/J code were replaced with ReentrantLocks. This allows carrier threads to unmount virtual threads when they are waiting on IO operations" (Bug #110512) — https://dev.mysql.com/doc/relnotes/connector-j/en/news-9-0-0.html
- **JEP 491** (JDK 24 반영): `synchronized` 로 인한 pinning 을 없앤다. 클래스 초기화 · 네이티브 프레임 등 일부 pinning 은 남는다. `jdk.tracePinnedThreads` 는 제거, 진단은 JFR `jdk.VirtualThreadPinned` — https://openjdk.org/jeps/491

## 가설과 반증 조건

| | 가설 | 지지 조건 | 반증 조건 |
|---|---|---|---|
| **H-pin** | JDK 21 + Connector/J 8.3.0 에서 `/send` VIRTUAL 이 느린 주원인은 드라이버의 monitor pinning 이다 | 격차 G = TPS(PLATFORM)/TPS(VIRTUAL) 가 **JDK 21 + CJ 9.7.0** 과 **JDK 25 + CJ 8.3.0** 양쪽에서 기준(JDK 21 + CJ 8.3.0)보다 작고, 두 조건의 95% 신뢰구간이 기준 구간과 겹치지 않으며, 그 조건들의 pinned 총시간이 기준의 5% 미만 | 두 조건 중 **하나라도** G 의 신뢰구간이 기준과 겹친다 |
| **H-mutex** | v1 의 H3(전역 락이 DB 와 외부 대기를 모두 감쌈)은 스레드 모델과 무관하게 직렬화한다 | `GLOBAL_ALL` 에서 TPS(VIRTUAL)/TPS(PLATFORM) 의 95% 신뢰구간이 JDK 21 · 25 모두에서 1 을 포함 | 어느 JDK 에서든 구간이 1 을 포함하지 않는다 |
| **H-sync-pin** | JDK 21 에서 락이 JDBC 만 감싸도(외부 대기는 락 밖) VIRTUAL 은 pinning 으로 추가 손실을 본다 | `GLOBAL_JDBC` 의 TPS(VIRTUAL)/TPS(PLATFORM) 가 JDK 21 에서 JDK 25 보다 작고 두 구간이 겹치지 않는다 | 구간이 겹친다 |
| **H-carrier** | JDK 21 + CJ 8.3.0 의 VIRTUAL `/send` 는 캐리어 수에 민감하고, 원인이 제거된 CJ 9.7.0 에서는 둔감하다 | CJ 8.3.0 에서 캐리어 1 → 32 의 TPS 비가 CJ 9.7.0 의 같은 비보다 크고 구간이 겹치지 않는다 | 구간이 겹친다 |

판정은 위 기준으로만 한다. 기준에 맞지 않으면 "판정 불가" 로 적는다.

## 제외 규칙 (측정 전에 고정)

실행을 분석에서 뺀다:
1. `state.txt` 가 `ok` 가 아님 (기동 실패 · 앱 사망 · 결과 없음)
2. 지표 서버 응답(`stat`)이 비었음
3. `whoami` 의 모델 · Java 주버전 · 드라이버 버전이 조건과 다름
4. 측정창 안 오류(`err`) > 0 — 뺀 뒤 따로 보고

뺀 실행은 지우지 않고 목록으로 보고한다. 한 조건에서 5회 중 2회 이상 빠지면 그 조건은 **판정에 쓰지 않는다.**

**불안정 표시** — 반복 5회 TPS 의 변동계수가 10% 를 넘으면 표에 "불안정" 을 붙인다. 판정 기준에 쓰는 조건이 불안정이면 판정을 "판정 불가" 로 한다.

## 분석

- 조건별 **중앙값**과 **부트스트랩 95% 신뢰구간**(반복 5회 재표집 10,000회)
- 격차 G 등 비율은 두 조건의 반복을 각각 재표집해 비율 분포를 만든 뒤 2.5% · 97.5% 분위
- 모든 표는 원자료(`results/v2/runs/*/`)에서 `v2/analyze.py` 가 다시 만든다. 손으로 옮기지 않는다

## 알려진 한계 (측정 전)

- closed-loop 부하다. 고정 도착률에서의 대기 시간은 이 설계로 답하지 않는다
- 앱 안 구간 평균은 "창 안에서 기록된 값" 기준이라, 대기가 창보다 긴 조건(전역 락 · 동시 1,000)에서는 구간 합이 총시간과 조금 어긋난다 (시험 실행에서 −9.8ms)
- 1 core 앱 · 한 호스트 · 한 DB 설정 · Connector/J 한 계열만 본다
- 호스트에 다른 컨테이너가 떠 있다. 끄지 않고 CPU 사용을 실행마다 기록한다

## 시험 실행 (결론에 쓰지 않음)

측정 도구 확인용으로 `results/v2/smoke/` 에 남긴다. 여기서 찾아 고친 것:
- 지연이 측정창보다 긴 조건에서 지연 표본이 0 → 창 안 완료 전체를 표본으로
- 앱이 포화되면 `/stat` 수집 실패 → 전용 지표 서버(8081)로 분리
- 창 종료 뒤 진행 중 요청을 모두 기다려 실행 1회 312초 → 5초만 기다림 (53초)
- JFR 텍스트 출력이 실행당 6MB → 요약 JSON 만 남김
- pinned 이벤트의 측정창 필터가 꺼져 있었다 — `run.sh` 가 Windows 파이썬에 `/c/...` 경로를 넘겨 창 시작 시각을 못 읽고 0 을 썼다. Windows 경로로 고치고, 읽지 못하면 0 대신 오류를 남기게 했다. 창 끝 경계도 추가
- 실행 1회 약 115초 (워밍업 30 · 측정 60 기준 시험 2회: 113 · 116초) → 본 측정 235회 ≈ 7.5시간
