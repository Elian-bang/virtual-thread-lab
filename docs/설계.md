# A-M9 설계 — Virtual Thread 는 언제 유효하고 언제 아닌가

## 이 실험이 답하려는 것

이력서에 이렇게 썼다.

> 발송이 외부 채널사 API 대기가 대부분인 **I/O 바운드**라는 점을 근거로,
> 1core 1GB 제약에서 **스레드 수를 늘리지 않고 동시성을 확보**하는 방식으로
> **Virtual Thread** 기반 비동기·병렬 구조 선택

**선택 근거는 있는데 숫자가 없다.** "얼마나 좋아졌나"에 답을 못 한다.

그리고 본인은 면접에서 이렇게 주장해 왔다.

> "진짜 병목은 스레드가 아니라 커넥션 풀입니다."

**이 주장이 맞는지도 아직 안 재봤다.** 이 실험은 둘 다 잰다.

---

## 가설 3개

| | 가설 | 틀리면 |
|---|---|---|
| **H1** | I/O 바운드 작업에서 Virtual Thread 가 고정 플랫폼 스레드 풀보다 처리량이 높다 | 이력서의 기술 선택 근거가 약해진다 |
| **H2** | **DB 커넥션 풀이 작으면 H1 의 이점이 사라진다.** 병목이 스레드에서 커넥션으로 옮겨간다 | "진짜 병목은 커넥션 풀" 주장이 틀린 것이다 |
| **H3** | Java 21 에서 `synchronized` 블록 안의 블로킹은 캐리어 스레드를 **pin** 시켜 VT 이점을 죽인다 | 코드에 `synchronized` 를 둬도 무방하다는 뜻이 된다 |

**H2 가 이 실험의 핵심이다.** H1 만 재면 "Virtual Thread 좋다"는 흔한 벤치마크다.
H2 는 *"그래서 언제 안 통하는가"* 에 답한다.

---

## 대상 작업 — 실제 발송 1건의 모양

```
① DB 에서 대상 조회        ← 커넥션 점유
② 외부 채널 API 호출        ← I/O 대기 (여기가 대부분)
③ DB 에 발송 결과 기록      ← 커넥션 점유
```

**①③ 이 커넥션을 잡고, ② 가 오래 기다린다.**
이 모양이라서 스레드를 늘려도 커넥션이 모자라면 소용이 없다. H2 는 이걸 잰다.

---

## 변수

| 기호 | 변수 | 값 |
|---|---|---|
| **M** | 실행 모델 | `PLATFORM` (고정 풀 200) · `CF` (CompletableFuture + 풀) · `VIRTUAL` |
| **C** | 동시 요청 | 100 · 500 · 1,000 · 2,000 |
| **P** | Hikari 커넥션 풀 | **10** · **50** |
| **S** | `synchronized` 사용 | off · on (H3 전용) |

주 스윕 `M × C × P` = **24 조건**, H3 검증 `VIRTUAL × S` = 2 조건.

## 고정 조건

운영과 같은 제약에서 재야 의미가 있다.

| | 값 | 왜 |
|---|---|---|
| 앱 컨테이너 | **`--cpus=1 --memory=1g`** | 이력서에 쓴 "1core 1GB 제약" 그대로 |
| 외부 채널 지연 | 50ms 고정 | I/O 바운드를 만드는 요소. 변동을 없애 비교 가능하게 |
| DB | MySQL 8.0 (별도 컨테이너, 제약 없음) | DB 가 병목이 되면 실험이 오염된다 |
| 반복 | 조건당 3회 | 1회는 노이즈와 구분이 안 된다 |
| 워밍업 | 매 조건 앞 15초 버림 | JIT · 커넥션 풀 예열 |

---

## 측정 항목

| 항목 | 출처 | 왜 재나 |
|---|---|---|
| TPS | 부하 생성기 | H1 |
| p50 / p95 / p99 | 부하 생성기 | 평균만 보면 꼬리를 놓친다 |
| **커넥션 획득 대기** | Hikari `ConnectionTimeoutRate`·`usage`/`acquire` 타이머 | **H2 의 직접 증거** |
| 활성 스레드 수 | JMX `ThreadMXBean` | "스레드를 안 늘렸다"는 주장의 근거 |
| **pinning 횟수** | JFR `jdk.VirtualThreadPinned` | **H3 의 직접 증거** |

**커넥션 획득 대기가 H2 의 핵심 지표다.**
TPS 가 안 오르는데 커넥션 대기가 치솟으면, 병목은 스레드가 아니다.

---

## 어떻게 하면 이 실험이 실패인가

미리 적어 둔다. 나중에 결과에 맞춰 해석을 바꾸지 않기 위해서다.

- **H1 이 틀리면** — 이력서 L74 의 "동시성 확보" 를 더 약하게 고치거나 뺀다.
- **H2 가 틀리면** — 면접에서 해 온 "진짜 병목은 커넥션 풀" 주장을 **철회한다.**
- 세 모델 차이가 노이즈 범위 안이면 — **"차이 없음"으로 적는다.** 없는 차이를 만들지 않는다.

---

# 설계 수정 (예비 측정 후)

예비 측정에서 **설계가 틀렸다는 것이 드러났다.** 고친 내용을 지운 자리 없이 적는다.

## 무엇이 틀렸나

첫 측정에서 `VIRTUAL` 이 `PLATFORM` 보다 **12배 느렸다** (81 vs 1,009 TPS).
가설과 정반대다. 여기서 결과를 해석하기 전에 **측정이 맞는지부터** 봤다.

| 실행 | conn=10 | conn=50 |
|---|---:|---:|
| PLATFORM | 169 TPS · 커넥션 대기 **259ms** | 1,009 TPS · 대기 8ms |
| VIRTUAL | 80 TPS · 대기 **0.03ms** | 84 TPS · 대기 0.01ms |

**VIRTUAL 은 커넥션을 기다리지 않았다.** 그런데도 느렸다.
커넥션 풀이 병목이라는 H2 의 전제 자체가 이 경우엔 성립하지 않는다.

pinning 스택을 보니 `sun.nio.ch.NioSocketImpl.park` — **소켓 I/O 였다.**
그리고 컨테이너 `nproc = 1` 이라 **가상 스레드 캐리어가 1개**뿐이었다.

## 결정적 확인 — CPU 는 고정하고 캐리어만 늘렸다

| 캐리어 | CPU | TPS |
|---:|---:|---:|
| 1 | 1 | 91 |
| 8 | 1 | 122 |
| **32** | **1** | **531** |

**CPU 를 한 개도 안 늘렸는데 5.8배가 됐다.**
CPU 병목도 커넥션 풀 병목도 아니다. **캐리어 스레드 병목이다.**
JDBC 드라이버가 캐리어를 붙잡고 놓지 않는다.

## 그래서 무엇이 바뀌나

**H2 를 다시 쓴다.**

| | 원래 | 고친 뒤 |
|---|---|---|
| H2 | 커넥션 풀이 작으면 VT 이점이 사라진다 | **플랫폼 스레드에서는 커넥션 풀이 진짜 병목이다. 그러나 가상 스레드에서는 커넥션 풀이 아니라 캐리어가 병목이다** |

본인 주장 *"진짜 병목은 스레드가 아니라 커넥션 풀"* 은 **절반만 맞다.**
플랫폼 스레드에서는 맞고 (169 → 1,009), 가상 스레드에서는 틀리다 (80 → 84).

**변수 두 개를 추가한다.**

| 기호 | 변수 | 값 | 왜 |
|---|---|---|---|
| **경로** | DB 접촉 여부 | `/sleep` (없음) · `/send` (있음) | 드라이버 몫과 가상 스레드 몫을 분리 |
| **W** | 캐리어 수 | 1 · 8 · 32 | 캐리어 병목의 직접 증거 |

`/sleep` 은 순수 I/O 대기만 한다. 여기서 나는 차이가 **가상 스레드 자체의 차이**고,
`/send` 와의 격차가 **드라이버 몫**이다.

## 예비 측정 — 대조군

| 1 core · 순수 I/O · 동시 500 | TPS | p50 | 스레드 |
|---|---:|---:|---:|
| PLATFORM | 2,921 | 154ms | 214 |
| **VIRTUAL** | **6,752** | **63ms** | **21** |

**H1 은 여기서 지지된다** — 스레드를 1/10 로 쓰고 처리량은 2.3배다.
이력서에 쓴 "스레드 수를 늘리지 않고 동시성을 확보" 가 이 조건에서는 사실이다.

**단, DB 를 건드리는 순간 뒤집힌다.** 그게 이 실험이 찾은 것이다.

# 설계 수정 2 — 위 예비 수치는 폐기한다

## 무엇을 발견했나

하네스를 고친 뒤 **같은 조건을 다시 돌렸더니 값이 완전히 달랐다.**

| 같은 조건 (VIRTUAL · conc=100 · conn=50 · `/send`) | 스레드 수 | TPS |
|---|---:|---:|
| 예비 측정 | 22 | 81 |
| 하네스 수정 후 | **415** | **376** |

4.6배 차이다. 둘 중 하나는 틀렸다.

## 원인 — ForkJoinPool 의 보상 스레드

가상 스레드 스케줄러는 ForkJoinPool 이다.
캐리어가 블로킹되면 **스케줄러가 캐리어를 더 만든다** — `maxPoolSize` 기본값 **256** 까지.

즉 캐리어 수는 `nproc` 로 고정된 값이 아니라 **상황에 따라 1에서 256 사이에서 움직인다.**
`threadCount` 22 는 보상이 안 일어난 상태, 415 는 끝까지 일어난 상태다.

**"캐리어가 1개라서 느리다"는 앞의 설명은 정확하지 않았다.**
캐리어는 1개로 시작하지만 늘어난다. 문제는 *늘어나기까지 걸리는 시간*과
*늘어나도 pinning 이 남아 있다는 점*이다.

## 하네스의 어디가 틀렸었나

준비 확인을 `/actuator/health` 로만 했다. **측정 경로인 `/send` 는 확인하지 않았다.**
1 core 에서는 JDBC 클래스 로딩과 Hikari 초기화가 느려서, health 가 200 을 줘도
`/send` 는 아직 데워지지 않은 상태였다. 그 상태로 잰 값이 예비 수치다.

고친 것:

- 준비 확인을 **실제 측정 경로**로 한다 (`/send` 또는 `/sleep` 이 200 을 줄 때까지)
- 준비에 실패하면 **부하를 걸지 않고 `SKIPPED` 로 표시한다** — 실패한 측정이 조용히 섞이지 않게
- 워밍업 15초 · 측정 20초로 늘린다

## 그래서

**위 "설계 수정" 절의 모든 수치는 폐기한다.**
지우지 않고 남겨 둔 것은, 틀린 측정을 어떻게 알아챘는지가 기록의 일부이기 때문이다.

결론은 **하네스를 고친 뒤 3회 반복으로 다시 잰 값에서만** 낸다.

# 설계 수정 3 — 측정값이 튄 진짜 이유는 하네스였다

앞의 "수정 2" 도 아직 부족했다. 같은 조건을 반복하면 **회차마다 10배씩 튀었다.**

| VIRTUAL · conc=100 · `/sleep` | TPS |
|---|---:|
| 어떤 회차 | 6,752 |
| 다른 회차 | 54.7 |
| 또 다른 회차 | 16.7 |

성능이 이렇게 튈 리가 없다. **측정 도구를 의심했다.**

## 결정적 단서

`/sleep` 은 **DB 를 한 줄도 안 건드린다.** 그런데 그 실행의 지표에 이렇게 찍혔다.

```
path=/sleep  ...  "connPending":88.0, "connActive":10.0, "connMax":10.0
```

커넥션 풀을 50 으로 줬는데 `connMax` 가 **10** 이다.
그리고 DB 를 안 쓰는데 88개가 대기 중이다.
**이 값은 이 실행의 것이 아니다. 직전 조건(conn=10)의 컨테이너가 답한 것이다.**

## 원인

매 조건마다 이렇게 했다.

```bash
docker rm -f vtlab-app
docker run -d --name vtlab-app ...     # 같은 이름
```

**Docker 내장 DNS 가 옛 IP 를 잠시 물고 있다.**
부하 생성기가 `vtlab-app` 으로 붙으면 죽은 IP 나 직전 컨테이너로 간다.
그래서 `ConnectException` 이 수만 건 나고, 지표는 남의 것이 섞였다.

## 고친 것

| | 무엇 | 왜 |
|---|---|---|
| 1 | 매 실행 **고유한 컨테이너 이름** | 이름 재사용 자체를 없앤다 |
| 2 | 이름 대신 **IP 로 접속** | DNS 를 경유하지 않는다 |
| 3 | 준비·종료·OOM 확인을 **그 IP 기준**으로 | 남의 컨테이너를 보지 않는다 |
| 4 | 에러 시 **백오프 20ms** | 없으면 느린 앱이 에러 폭풍이 된다. 그러면 재는 것이 처리량이 아니라 재시도 속도다 |
| 5 | `-Xmx512m -Xss512k` | CF 모델은 Tomcat 200 + 풀 200 = 400 스레드다. 1GB 를 넘겨 컨테이너가 죽었다 |
| 6 | 죽으면 **`DIED` 로 표시하고 값을 안 남긴다** | 죽은 실행의 숫자를 결과로 쓰지 않는다 |

## 고친 뒤 — 재현된다

| 모델 (conc=100 · `/sleep`) | 1회 | 2회 | 플랫폼 스레드 | 에러 |
|---|---:|---:|---:|---:|
| PLATFORM | 1,831 | 1,872 | 114 | 0 |
| CF | 1,751 | 1,855 | 114 | 0 |
| **VIRTUAL** | **1,892** | **1,894** | **17** | 0 |

오차 2% 이내, 에러 0.

**이 커밋 이전의 모든 측정값은 무효다.** 결론은 여기서부터 나온 값으로만 낸다.

## 남겨 두는 이유

틀린 수치를 지우고 맞는 수치만 올릴 수도 있었다. 그러지 않았다.

**측정이 틀렸다는 것을 무엇으로 알아챘는지가 이 실험의 내용이기 때문이다.**
`/sleep` 실행에 `connMax=10` 이 찍힌 것 — 그 한 줄이 없었으면
10배 튀는 값을 "가상 스레드는 불안정하다" 로 잘못 결론냈을 것이다.
