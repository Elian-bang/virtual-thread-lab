## 결론

1. **JDK 21 + Connector/J 8.3.0 에서 VIRTUAL `/send` 가 느린 원인은 드라이버 안의 pinning 이다 (H-pin 지지).**
   드라이버를 9.7.0 으로 바꾸거나 JDK 를 25 로 바꾸면, 둘 중 **하나만 바꿔도** PLATFORM 과의 격차가 16.4배에서 1.04~1.05배로 줄고 pinned 이벤트가 0 이 된다.
2. **캐리어 수를 늘리면 좋아지는 현상도 같은 원인에서 나온다 (H-carrier 지지).**
   CJ 8.3.0 에서는 캐리어 1 → 32 에 TPS 가 14.2배 오르지만, CJ 9.7.0 에서는 1.04배다.
3. **우리 코드의 `synchronized` 가 JDBC 만 감쌀 때, JDK 21 에서 pinning 으로 추가 손해를 본다는 가설은 반증됐다 (H-sync-pin 반증).**
   pinning 은 실제로 생기지만(JDK 21 에서만), 락 자체가 병목이라 TPS 차이로 드러나지 않는다.
4. **전역 락이 외부 대기까지 감싸면 스레드 모델과 무관하게 직렬화된다는 가설은 사전 기준으로 반증됐다 (H-mutex 반증).**
   다만 반증 근거는 JDK 25 에서 VIRTUAL 이 1.4% 느린 것 하나다. 두 모델 모두 초당 약 16건으로 직렬화된 것은 사실이다. 기준은 측정 뒤에 바꾸지 않는다.
5. **v1 의 "VT 가 DB 경로에서 느리다" 는 JDK 21 · CJ 8.x 조합에 한정된 결과였다.** 원인이 없는 조합에서 VIRTUAL 은 PLATFORM 과 비슷하다 (1.3~5% 느림).

## 1. H-pin — 원인을 없애면 격차가 닫히는가

`/send` · 동시 100 · 풀 50 · 락 없음

| JDK | Connector/J | PLATFORM TPS | VIRTUAL TPS | 격차 G = P/V | VIRTUAL pinned 총시간 |
|---:|---|---:|---:|---|---:|
| 21 | 8.3.0 (기준) | 1335.0 | 81.5 | **16.38** [13.79, 17.39] | 55,039 ms |
| 21 | 9.7.0 | 1329.5 | 1265.2 | **1.05** [1.03, 1.06] | 0 |
| 25 | 8.3.0 | 1333.0 | 1284.6 | **1.04** [1.02, 1.04] | 0 |
| 25 | 9.7.0 | 1328.1 | 1278.9 | **1.04** [1.03, 1.05] | 0 |

판정 기준: JDK21·CJ9.7 과 JDK25·CJ8.3 **둘 다** 격차 구간이 기준과 겹치지 않고 pinned 총시간이 기준의 5% 미만 → 둘 다 충족 → **지지**.
동시 1,000 도 기준에 따라 지지 (기준 1.53 [1.36, 1.57] → 1.08 / 1.02 / 1.00). 단 동시 1,000 은 아래 "측정 뒤 발견한 문제" 때문에 해석에 주의.

### pinning 이 어디서 생기는가

JDK 21 · CJ 8.3.0 의 VIRTUAL 실행에서 JFR `jdk.VirtualThreadPinned` 이벤트의 상위 스택은 모든 조건에서 **하나**였다.

```
sun.nio.ch.NioSocketImpl$1.read
 <- java.net.Socket$SocketInputStream.read
 <- com.mysql.cj.protocol.ReadAheadInputStream.fill
 <- com.mysql.cj.protocol.ReadAheadInputStream.readFromUnderlyingStreamIfNecessary
 <- com.mysql.cj.protocol.ReadAheadInputStream.read
```

DB 응답을 소켓에서 읽는 동안 가상 스레드가 캐리어에서 내려오지 못한다. 이것이 드라이버의 `synchronized` 때문이라는 것은 스택만으로는 확정하지 않는다. 대신 **두 가지 제거 실험이 같은 방향**을 가리킨다.
- CJ 9.0.0 릴리스 노트: 드라이버의 synchronized 블록을 ReentrantLock 으로 교체 → 9.7.0 에서 이벤트 0
- JEP 491 (JDK 24): monitor 로 인한 pinning 제거 → JDK 25 에서 이벤트 0

### 느린 이유는 CPU 가 아니라 "실행 차례"

| 조건 (동시 100 · 풀 50) | TPS | 앱 CPU | 앱 안 DB 평균 | 앱 안 외부 대기 평균 (실제 대기 50ms) |
|---|---:|---:|---:|---:|
| PLATFORM · JDK21 · CJ8.3 | 1335.0 | 0.60 | 23.5 ms | 50.2 ms |
| VIRTUAL · JDK21 · CJ8.3 | 81.5 | **0.10** | 12.3 ms | **614.1 ms** |
| VIRTUAL · JDK21 · CJ9.7 | 1265.2 | 0.30 | 26.6 ms | 50.6 ms |

VIRTUAL 은 CPU 를 10% 만 쓰는데, 50ms 짜리 sleep 이 끝나고 다시 실행되기까지 평균 614ms 가 걸린다. 캐리어가 DB 소켓 읽기에 붙잡혀 있어 깨어난 가상 스레드가 올라탈 자리가 없다는 뜻이다.

## 2. H-carrier — 캐리어 수에 민감한가

VIRTUAL `/send` · 동시 100 · 풀 50 · JDK 21

| 캐리어 | CJ 8.3.0 TPS | 외부 대기 평균 | pinned 총시간 | CJ 9.7.0 TPS |
|---:|---:|---:|---:|---:|
| 1 | 81.2 | 630.5 ms | 55,103 ms | 1279.3 |
| 2 | 87.0 | 571.0 ms | 112,257 ms | |
| 4 | 121.8 **불안정** (CV 14.6%) | 363.4 ms | 226,435 ms | |
| 8 | 373.3 | 182.3 ms | 452,760 ms | 1330.0 |
| 16 | 699.5 | 95.0 ms | 860,677 ms | |
| 32 | 1152.1 | 58.7 ms | 1,484,378 ms | 1331.6 |
| **32/1** | **14.19** [13.87, 15.72] | | | **1.04** [1.01, 1.05] |

→ **지지.** 캐리어를 늘리는 것은 원인을 없애는 것이 아니라 붙잡힐 캐리어를 더 주는 것이다. pinned 총시간이 캐리어 수에 비례해 늘어나는 것이 그 흔적이다 (총시간은 모든 가상 스레드의 합이라 벽시계 시간보다 크다).
캐리어 32 에서도 CJ 9.7.0 의 캐리어 1 보다 느리다 (1152.1 < 1279.3).

## 3. H-mutex · H-sync-pin — 우리 코드의 `synchronized`

`/send` · 동시 100 · 풀 50 · **CJ 9.7.0** (드라이버 원인을 없앤 상태에서 우리 락만 남김)

| 락 범위 | JDK | PLATFORM TPS | VIRTUAL TPS | V/P [95%] | VIRTUAL pinned |
|---|---:|---:|---:|---|---:|
| 전역 (DB + 외부 대기) | 21 | 15.8 | 15.8 | 1.0000 [0.9924, 1.0045] | 58,632 ms |
| 전역 (DB + 외부 대기) | 25 | 15.8 | 15.6 | 0.9860 [0.9811, 0.9968] | 0 |
| JDBC 만 | 21 | 86.1 | 78.7 | 0.9139 [0.8681, 0.9438] | 54,655 ms |
| JDBC 만 | 25 | 82.8 | 75.5 | 0.9122 [0.8614, 0.9884] | 0 |

- **H-mutex 반증** — 기준은 "두 JDK 모두 구간이 1 을 포함". JDK 21 은 포함, JDK 25 는 상한 0.9968 로 포함하지 않는다. 실질 차이는 초당 0.2건이다. 전역 락 아래에서는 두 모델 모두 초당 약 16건(= 1건당 약 63ms 직렬 처리)으로 떨어지므로, v1 의 H3 "synchronized 가 pin 해서 3.9배" 는 pinning 이 아니라 **직렬화**였다는 v1 정정 내용은 그대로 유지된다.
- **H-sync-pin 반증** — JDK 21 과 25 의 비율이 0.91 로 같다. JDK 21 VIRTUAL 은 pinned 이벤트가 있고 외부 대기도 642.6ms 로 늘었지만 (스택: 우리 락 안의 드라이버 소켓 읽기), 락을 기다리는 시간이 훨씬 커서 TPS 차이로 이어지지 않았다.
- JDBC 만 감싼 락에서 VIRTUAL 이 두 JDK 모두 약 9% 느린 이유는 이 실험으로 설명하지 못한다.

## 측정 뒤 발견한 문제 (판정 기준은 바꾸지 않음)

### 동시 1,000 `/send` 는 같은 행 UPDATE 경합에 막혀 있다

부하 생성기가 요청마다 `seq = 작업자번호 × 1,000,000 + n` 을 보내고 앱은 `id = seq % 1000 + 1` 을 쓴다. `1,000,000 % 1000 = 0` 이므로 **모든 작업자가 같은 순서로 같은 행을 갱신한다.** v1 도 같은 방식이었다.

MySQL `Innodb_row_lock_time` 전후 차이 (실행 1회 = 워밍업 30초 + 측정 60초 + 정리, 5회 중앙값):

| 조건 (JDK21 · CJ8.3 · 풀 50) | 행 락 대기 횟수 | 행 락 대기 총시간 | 커넥션 획득 대기 평균 |
|---|---:|---:|---:|
| PLATFORM · 동시 100 | 21,382 | 452,473 ms | 1.0 ms |
| PLATFORM · 동시 1000 | 11,050 | **4,578,106 ms** | 531.6 ms |
| VIRTUAL · 동시 100 (느림) | 390 | 3,652 ms | 0.0 ms |

- 동시 1,000 에서 행 락 대기 총시간이 약 4,578초다. 실행 약 95초 동안 평균 48개 안팎의 연결이 행 락을 기다린 셈이라 풀 50 이 거의 모두 묶인다
- 그래서 동시 1,000 `/send` 는 모델 · JDK · 드라이버와 무관하게 **약 120~135 TPS** 로 모인다. 이 칸의 격차 G 가 1 에 가깝다는 것은 "원인이 사라졌다" 와 "DB 행 락이 먼저 막았다" 를 구분하지 못한다
- 동시 100 도 행 락 대기가 있지만 (PLATFORM 약 452초 → 평균 5개 안팎), 모든 비교 칸에 같은 조건이라 H-pin · H-carrier · H-mutex 판정에 쓴 동시 100 비교는 유지한다
- 동시 1,000 에서 왜 이렇게까지 무너지는지(대기자가 많을 때 InnoDB 락 대기 · 교착 탐지 비용)는 **추론이며 측정하지 않았다**

### 그 밖의 한계

- **앱 안 "기타" 가 음수** — 대기가 측정창보다 긴 조건(동시 1,000, VIRTUAL · CJ9.7 등)에서 −100 ~ −187ms. 구간별 평균이 서로 다른 요청 집합에서 기록되기 때문이다
- **앱 안 DB 시간에 커넥션 획득 대기가 포함** — 동시 1,000 VIRTUAL 의 "DB 8,483ms" 는 대부분 풀 대기다
- **pinned 총시간은 모든 가상 스레드의 합** — 벽시계 시간보다 클 수 있다
- 캐리어 4 는 불안정 (CV 14.6%) — H-carrier 판정에는 1 · 32 만 쓴다
- closed-loop 부하 · 앱 1 core · 호스트 하나 · MySQL 설정 하나 · Connector/J 한 계열. 고정 도착률에서의 대기 시간은 답하지 않는다
- 호스트에 다른 컨테이너가 떠 있었다 (실행마다 `others_before/after.txt` 에 기록)
