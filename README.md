# virtual-thread-lab

**Virtual Thread 는 언제 유효하고 언제 아닌가를 1 core 1GB 에서 잰 기록.**

> ⚠️ **정정 (2026-09-14)** — 외부 리뷰를 받고 코드와 원자료를 다시 검토했다. **v1 결론 일부는 틀렸거나 증명되지 않았다.**
> 원자료는 그대로 두고 결론만 증거 수준에 맞게 낮췄다. 무엇이 틀렸는지는 아래 [정정](#정정-2026-09-14) 절에 있다.
> 원인 검증은 v2 에서 다시 한다.

"I/O 바운드니까 Virtual Thread" 라고 답해 왔는데, 얼마나 좋아지는지 숫자가 없었다. 그래서 쟀다.

측정 조건 26개 · 각 3회 · 총 78회. 측정 도구 오염으로 버린 실행은 [`results/폐기_오염측정.tsv`](results/폐기_오염측정.tsv) 에 따로 남겼다.

## 관측된 것 — 원자료로 뒷받침되는 범위

### DB 를 안 건드릴 때 (`/sleep` · 외부 대기 50ms)

| 동시 | PLATFORM | VIRTUAL | 플랫폼 스레드 수 |
|---:|---:|---:|---|
| 100 | 1,965 | 1,906 | 115 → **17** |
| 500 | 3,585 *(편차 14%)* | **7,138** | 214 → **17** |
| 2,000 | 3,747 *(편차 22%)* | **5,875** | 214 → **17** |

<sub>TPS · 3회 중앙값. 편차 = (최대−최소)/중앙값. "동시 N" 은 부하 생성기가 N 개 요청을 쉬지 않고 보내는 closed-loop 다.
스레드 수는 `ThreadMXBean` 최대값이라 캐리어와 JVM 내부 스레드를 포함한다.</sub>

- 동시 100 에서는 차이가 없고, 500 에서 약 2배다. PLATFORM 쪽 반복 편차가 14% 라 배율은 대략값이다.
- 가상 스레드 모델은 모든 동시 수준에서 플랫폼 스레드 17개로 돌았다.

### DB 를 건드릴 때 (`/send` · JDBC 2회 + 외부 대기 50ms)

| 조건 | PLATFORM | VIRTUAL | 배율 |
|---|---:|---:|---:|
| 동시 100 · 풀 10 | 234.1 | 84.6 | 2.8× |
| 동시 100 · 풀 50 | 1,109.0 | 86.6 | 12.8× |
| 동시 1,000 · 풀 10 | 143.4 | 131.3 | 1.1× |
| 동시 1,000 · 풀 50 | 149.5 | 130.4 | 1.1× |

- 이 환경에서 가상 스레드는 DB 를 건드리는 작업에서 플랫폼 스레드보다 느렸다.
  **배율이 조건에 따라 1.1~12.8배로 크게 달라, 한 숫자로 요약할 수 없다.**
- 가상 스레드는 커넥션 풀을 10 → 50 으로 늘려도 TPS 가 거의 그대로였다 (84.6 → 86.6).

### 캐리어 수에 민감하다

CPU 쿼터는 1개로 두고, `parallelism` 과 `maxPoolSize` 를 같은 값으로 고정해 캐리어만 바꿨다.

| 캐리어 | 1 | 8 | 32 |
|---|---:|---:|---:|
| TPS | 86.6 | 143.7 | 614.2 |

캐리어를 늘리자 TPS 가 올랐다. **여기까지가 관측이다.**
"JDBC 드라이버가 소켓 대기 중 캐리어를 pin 해서 느리다" 는 **가설**이다.
그 근거로 적었던 pinning 스택은 저장되지 않았고, 원인을 없애 보는 실험(JDK 24, 다른 드라이버 버전)도 하지 않았다.

전체 판정은 [`results/결과.md`](results/결과.md).

## 해 오던 말은 어떻게 됐나

| 해 오던 말 | 지금 말할 수 있는 것 |
|---|---|
| "I/O 바운드니까 Virtual Thread" | **조건부.** DB 없는 대기에서는 동시 500 이상에서 유리했고, DB 를 건드리는 작업에서는 이 환경에서 불리했다 |
| "진짜 병목은 스레드가 아니라 커넥션 풀" | **플랫폼 스레드에서는 지지** (풀 10 → 50 에 TPS 4.7배). 가상 스레드에서는 풀을 늘려도 변화가 없었지만, 무엇이 병목인지는 아직 증명하지 못했다 |
| "스레드를 안 늘리고 동시성 확보" | **지지.** 가상 스레드 모델은 모든 동시 수준에서 플랫폼 스레드 17개 |

## 정정 (2026-09-14)

| v1 에서 쓴 것 | 실제 | 근거 |
|---|---|---|
| "`synchronized` 가 캐리어를 pin 해서 3.9배 느려진다" (H3) | **무효.** 락 하나가 JDBC 와 50ms 외부 대기까지 감싸, 스레드 모델과 무관하게 모든 요청을 한 줄로 세운다. pinning 과 상호배제를 구분할 수 없다 | `app/src/main/java/dev/elian/vt/SendService.java` — `synchronized (lock) { doSend(...) }` |
| "pinning 스택이 `NioSocketImpl.park` — JDBC 드라이버가 캐리어를 붙잡는다" | **저장된 스택이 없다.** 설계 문서가 폐기한 오염 측정 시기의 관측이다. `pinned` 칸은 컨테이너 로그의 `onPinned` 줄 수라 pinning 발생 횟수가 아니다 | `run.sh` — `grep -c "onPinned"` 뒤 `docker rm -f` |
| TPS | **지연이 큰 조건에서 부풀려졌다.** 측정 종료 신호 뒤에 끝난 진행 중 요청도 성공으로 세고 20초로 나눈다. 지연이 긴 동시 1,000 `/send` 와 sync=on 조건에서 영향이 클 것으로 본다 | `loadgen/LoadGen.java` — `stop.set(true)` 뒤 executor 종료 대기 |
| "같은 코드가 12.8배 느려지기도 한다" | 12.8배는 네 조건 중 가장 큰 한 칸이다. 나머지는 2.8× · 1.1× · 1.1× | `results/집계.md` B 표 |
| "반복 폭은 대부분 2% 이내" | 26개 조건 중 12개뿐이다. 위 표의 PLATFORM 동시 500·2,000 은 14% · 22% | `results/집계.md` 최소~최대 |
| "스레드 214 → 17, 전 구간 1/12.6" | 동시 100 은 **115 → 17** (1/6.8). 214 는 동시 500 이상에서만 | `results/raw.tsv` |

## 이 저장소에서 더 중요한 것 — 측정을 어떻게 믿을 수 있게 만들었나

처음 잰 값은 회차마다 **10배씩 튀었다.** 6,752 → 54.7 → 16.7 TPS.
"가상 스레드는 불안정하다" 로 결론낼 뻔했다. **원인은 전부 측정 도구였다.**

| 증상 | 원인 | 무엇으로 알아챘나 |
|---|---|---|
| 값이 10배 튐 | 컨테이너 이름 재사용 → Docker DNS 가 옛 IP 를 물어 **직전 조건에 부하가 걸림** | DB 를 안 쓰는 `/sleep` 실행에 `connMax=10` 이 찍힘 |
| 에러 수만 건 | 백오프 없는 재시도 → 느린 앱이 **에러 폭풍**으로 | ok 보다 err 이 20배 |
| 값이 또 흔들림 | 스윕 두 개가 **동시 실행** | 결과가 78줄이어야 하는데 134줄, block 이 A/B 로 교차 |
| 일부 실행이 죽음 | **원인 미확인** — 기록된 중단 3건은 `oom=` 칸이 비어 있다 (정정 절 참고) | 컨테이너 종료 감지 |

`connMax=10` 한 줄이 없었으면 잡음을 결과로 발표했을 것이다.

도구가 지키는 규칙은 [`docs/하네스.md`](docs/하네스.md).
틀린 수치는 지우지 않고 [`docs/설계.md`](docs/설계.md) 에 **폐기 표시로 남겼다** —
무엇으로 알아챘는지가 기록의 일부다.

## 한계

- **1 core 만 쟀다.** 운영 제약이 그래서다. 코어가 늘면 캐리어도 늘어 그림이 달라질 수 있다.
- **DB · 호스트 조건을 기록하지 않았다.** DB 컨테이너는 자원 제한이 없고, MySQL 정확한 버전·호스트 사양·CPU 사용률이 남아 있지 않다.
- **드라이버 하나만 쟀다.** Connector/J 8.3.0.
- **작업 비율이 고정이다.** 외부 대기 50ms 에 JDBC 2회.
- **Java 24(JEP 491)는 안 쟀다.** `synchronized` 로 인한 pinning 이 거기서 해소된다고 알려져 있다 — 이 저장소에서 확인하지 않았다.
