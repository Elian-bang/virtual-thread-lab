# virtual-thread-lab

**Virtual Thread 는 언제 유효하고 언제 아닌가를 1 core 1GB 에서 잰 기록.**

"I/O 바운드니까 Virtual Thread" 라고 답해 왔는데, **얼마나 좋아지는지 숫자가 없었다.**
그래서 쟀다. 그리고 그 답이 절반은 틀렸다는 것을 알았다.

측정 조건 26개 · 각 3회 · 총 78회 · 버린 실행 0회.

---

## 결과 한 장

**같은 코드가 조건에 따라 2배 빨라지기도, 12.8배 느려지기도 한다.**

### DB 를 안 건드릴 때 — VT 가 이긴다

| 동시 | PLATFORM | VIRTUAL | 플랫폼 스레드 |
|---:|---:|---:|---|
| 100 | 1,965 | 1,906 | 214 → **17** |
| 500 | 3,585 | **7,138** | 214 → **17** |
| 2,000 | 3,747 | **5,875** | 214 → **17** |

동시 100 에서는 이점이 없다. **500 부터 2배.** 스레드는 전 구간 **1/12.6**.

### DB 를 건드리면 — 뒤집힌다

동시 100, 커넥션 풀만 10 → 50

| 모델 | conn=10 | conn=50 | 배율 | 커넥션 대기 |
|---|---:|---:|---:|---|
| PLATFORM | 234 | **1,109** | 4.7× | 168.7ms → 5.1ms |
| **VIRTUAL** | 84.6 | 86.6 | **1.02×** | **0.0ms → 0.0ms** |

**커넥션을 한 번도 안 기다렸는데 12.8배 느리다.**

병목은 커넥션 풀이 아니라 **캐리어**였다. CPU 를 1개로 고정하고 캐리어만 늘렸더니

| 캐리어 | 1 | 8 | 32 |
|---|---:|---:|---:|
| TPS | 86.6 | 143.7 | **614.2** |

**CPU 를 하나도 안 늘렸는데 7.1배.**
pinning 스택이 `sun.nio.ch.NioSocketImpl.park` 를 가리킨다 —
**JDBC 드라이버가 소켓 대기 중 캐리어를 붙잡는다.**

전체 판정과 근거는 [`results/결과.md`](results/결과.md).

## 그래서 무엇이 바뀌었나

| 해 오던 말 | 측정 후 |
|---|---|
| "I/O 바운드니까 Virtual Thread" | **부족하다.** 같은 I/O 바운드라도 **그 I/O 를 누가 하느냐**가 가른다 |
| "진짜 병목은 스레드가 아니라 커넥션 풀" | **플랫폼 스레드에서만 맞다.** 가상 스레드로 바꾸면 틀린다 |
| "스레드를 안 늘리고 동시성 확보" | **맞다.** 214 → 17, 전 구간 |

## 이 저장소에서 더 중요한 것 — 측정을 어떻게 믿을 수 있게 만들었나

처음 잰 값은 회차마다 **10배씩 튀었다.** 6,752 → 54.7 → 16.7 TPS.
"가상 스레드는 불안정하다" 로 결론낼 뻔했다. **원인은 전부 측정 도구였다.**

| 증상 | 원인 | 무엇으로 알아챘나 |
|---|---|---|
| 값이 10배 튐 | 컨테이너 이름 재사용 → Docker DNS 가 옛 IP 를 물어 **직전 조건에 부하가 걸림** | DB 를 안 쓰는 `/sleep` 실행에 `connMax=10` 이 찍힘 |
| 에러 수만 건 | 백오프 없는 재시도 → 느린 앱이 **에러 폭풍**으로 | ok 보다 err 이 20배 |
| 값이 또 흔들림 | 스윕 두 개가 **동시 실행** | 결과가 78줄이어야 하는데 134줄, block 이 A/B 로 교차 |
| 일부 실행이 죽음 | CF 모델은 Tomcat 200 + 풀 200 = **400 스레드**, 1GB 초과 | `OOMKilled=true` |

`connMax=10` 한 줄이 없었으면 잡음을 결과로 발표했을 것이다.

도구가 지키는 규칙은 [`docs/하네스.md`](docs/하네스.md).
틀린 수치는 지우지 않고 [`docs/설계.md`](docs/설계.md) 에 **폐기 표시로 남겼다** —
무엇으로 알아챘는지가 기록의 일부다.

## 돌려보기

```bash
docker run -d --name vtlab-db -e MYSQL_ROOT_PASSWORD=labpass -e MYSQL_DATABASE=vtlab mysql:8.0
docker network create vtlab-net && docker network connect vtlab-net vtlab-db
./run.sh VIRTUAL 500 50 false 15 20 /sleep 1    # 모델 동시 커넥션 sync 워밍업 측정 경로 CPU
./chunk.sh 1 10                                  # conditions.txt 의 1~10줄
```

## 한계

- **1 core 만 쟀다.** 운영 제약이 그래서다. 코어가 늘면 캐리어도 늘어 그림이 달라진다.
- **드라이버 하나만 쟀다.** Connector/J 8.3.0.
- **작업 비율이 고정이다.** 외부 대기 50ms 에 JDBC 2회.
- **Java 24(JEP 491)는 안 쟀다.** `synchronized` pinning 은 거기서 해소된다.
